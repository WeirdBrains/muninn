Live collaboration and peers

Since 2.19, nodes that exchanged keys can work together as it happens. You can message each other, edit the same entry, journal, code space or record at once and see each other's cursors, and run each other's served executables. The peers view shows who you're connected to and what each of them has for you.

Collaboration works over any active key exchange that is a connection (node scope), a linked node of yours, or an org membership. Share-only exchanges can't collaborate.

Peers

mnnn peers                     # your peers: label, how you're connected, sites, unread messages
mnnn peers show ben            # what ben has for you
mnnn peers run comet-lab comet-lab sightings --input '{"op": "query"}'
mnnn peers request ben "could you share the field notes journal?"

peers show asks the peer what it offers you:

  • items it shares with you (open them with mnnn net fetch)
  • live sessions it invited you to (mnnn live join)
  • org executables you may run (mnnn peers run)
  • sites it announced

A peer is named by its connection label, its exchange, its node label, its peer id, or (for an org membership) the org's slug or name.

peers request sends a message about request:peers; that's how you ask for a share, an invitation or access.

Messages

mnnn msg send ben "the comet is back" --about journal:4f2a
mnnn msg list                 # everything, oldest first (● unread, → sent, ← received)
mnnn msg list ben --unread
mnnn msg list --about journal:4f2a
mnnn msg read                 # mark all read (or: mnnn msg read ben)

Each message is kept on both nodes and syncs to each side's linked nodes. If the peer can't be reached, the message stays marked waiting, and your running node retries it (only the node that wrote a message sends it, so linked nodes never send it twice).

An arriving message is a net.message action. It shows up in history and as a notification that links to the conversation, and rule sets can trigger on it (--on net.message, with the fields from, peer, about and text).

Live sessions

The node that has the item hosts the session and invites peers:

mnnn live share entry 4f2a --with ben --with cleo
mnnn live share journal "field notes" --with ben     # every entry of the journal
mnnn live share code calc --with ben
mnnn live share record Sightings/9c1e --with ben     # MODEL/RECORD
mnnn live list
mnnn live stop 7d0c

The host's node must be running (mnnn net start) to answer guests. A guest joins the session and then edits it:

mnnn peers show anna                       # lists the session
mnnn live join anna 7d0c
mnnn live show 7d0c                        # the text now and who is here
mnnn live watch 7d0c                       # follow it as it changes (pushed over a stream)
mnnn live edit 7d0c                        # in $VISUAL/$EDITOR
mnnn live edit 7d0c --value "new text" --cursor 8
mnnn live edit 7d0c 1e9b --value "…"       # one entry of a journal session
mnnn live edit 7d0c mag --value 4.7        # a record field (a JSON value)
mnnn live stop 7d0c                        # a guest leaves
  • Merging. Every edit becomes a set of operations, and they merge without loss.
    • Text (entry bodies, journal entries, code sources) is a replicated text: if two people type at the same place, both insertions are kept, and a deletion never removes text it didn't see.
    • Record fields are last writer wins, per field.
  • Writing back. The host writes the merged text back to the item, so it syncs to the host's linked nodes like any edit. Edits the host makes to the item some other way (the TUI, the CLI, a rule) become operations too.
  • Presence. Each round also says where your cursor is. live show lists who was here in the last 30 seconds and at which offset; the TUI marks their cursors in the text.
  • Who may join. Only the peers the host invited can join. A guest can't forge another node's operations, close the session or send run results.
  • Journals. A journal session covers the journal's existing entries. New entries written on the host join it; guests can't create entries.
  • Code. A code space edited live changes its source, so it has to be approved again before it runs, as with any edit.
  • History. History records live.host, live.stop, and live.edit (at most one per guest per minute).

Running a peer's executables

mnnn peers run PEER ORG ENDPOINT --input JSON calls one of the org endpoints on the peer's node, the same way an org call does: the peer checks your membership and your role's permission for that endpoint (records.read, records.write, …), and code endpoints only run approved code. The output comes back in chunks of a run session (you'll see progress on stderr), and the whole result is printed as JSON. The peer records a live.run action.

In the TUI

W (or Net ▸ Peers, messages & live…) opens the Peers window with three tabs:

  • Peers: Enter asks the selected peer what it offers. m messages it, a asks it for something, J joins an offered live session, s shares one of your items live with it, and x runs one of its executables (ORG ENDPOINT [JSON]).
  • Messages: the conversation with the selected peer. m writes and r marks it read.
  • Live: your sessions. Enter shows the text with everyone's cursors, e edits a document, and x stops (host) or leaves (guest).

Transports

Collaboration has two transports. Both carry the same muninn.live.v1 messages, and consent, invitations and roles are checked the same way on both.

  • stream (the default): a gRPC bidirectional stream (muninn.live.v1.Live/Open) straight to the peer's node. The host pushes every change to a live session (operations, presence and cursors) as it happens, guests send their edits on the same stream, and messages and remote-run output use it too. The channel is TLS 1.3, and both sides prove their node identity with their identity key (libp2p TLS certificates), so the peer on the stream is the peer id its key exchange names. Each call also names its key exchange, which must be active and belong to that peer.
  • poll: requests over the existing peer connection (libp2p with Noise, sealed with the exchange's keys). It works anywhere the node works, including through relays, and guests ask about once a second while following a session. Use it where a node can't take incoming TCP, for example inside a container.

Choose one, in order of precedence:

mnnn --transport poll live watch 7d0c          # this command only
export MUNINN_COLLAB_TRANSPORT=poll            # this environment
mnnn net config --collab-transport poll        # the setting (net.collab_transport)

Ports and firewalls

The running node (mnnn net start, or the TUI's node) listens for streams on TCP 4742 on all interfaces (the peer connection itself uses 4741):

mnnn net config --collab-port 4742 --collab-bind 0.0.0.0
mnnn net config --collab-advertise alien.duckdns.org:4742   # behind NAT with a port forward

Allow TCP 4742 in the host firewall (and forward it on the router for peers outside your network). A peer finds the listener by asking over the peer connection (Hello): it gets the port, and any advertised addresses, then dials the node's known addresses on that port. mnnn net start prints where the listener is. If the port is taken, the node still runs: it records net.collab.fallback and peers poll it.

Falling back

A node set to stream uses polling for a peer, automatically, when:

  • the peer uses poll (mixed nodes work together, over polling)
  • the peer runs no listener
  • the listener doesn't answer within a few seconds (NAT, a firewall, relay-only reachability)

It records why as a net.collab.fallback action (see mnnn history list) and polls that peer for the next 10 minutes before trying a stream again, so collaboration still works through relays. mnnn live show --json and mnnn live watch --json say which transport was used ("transport").

Containers

In a container that doesn't publish a port for the listener, use polling:

docker run -e MUNINN_COLLAB_TRANSPORT=poll … mnnn net start

Or publish the port (-p 4742:4742) and set --collab-advertise HOST:4742 to the address peers can reach, to use streams. Muninn doesn't ship a container image; set this in your own.

How it travels (design notes)

  • Wire format. Sessions speak muninn.live.v1, protobuf messages defined in proto/muninn/live/v1/live.proto: Batch, Frame and Op (insert, delete, set field, cursor, run chunk, closed).
  • The boundary. Everything goes through crate::collab::wire: a Transport trait (call, follow) with two implementations (Libp2p for polling, StreamTransport in crate::collab::stream), and one serve function that answers both. Pushes come from session::pull, which checks invitations like any other round.
  • Building. The gRPC service is generated at build time from the .proto with a pure-Rust compiler (protox), so building Muninn doesn't need protoc.
  • Ordering. The host keeps the operation log and its order. Guests send their operations and get back everything after the last one they have, so every copy applies the same operations in the same order.
  • Node-local data. Sessions, operations and presence stay on the node. Only the merged item and the messages sync to linked nodes.
  • Run results. A remote run is computed on the host, then its output streams back in chunks (pushed over a stream, polled otherwise). The computation itself isn't streamed while it runs.
